# Xeroww V0.10 and V0.11 Implementation Plan

## 1. Purpose

This plan defines one coordinated implementation program for:

- V0.10 Replay and Behaviour Lab
- V0.11 Portfolio Intelligence

The two capabilities will be designed and implemented together because they share the same core requirements: immutable decisions, point-in-time market state, durable event history, reproducible calculations, explicit formulas, tenant isolation, and compact explainability.

The public release should move to V0.11 only after both milestones pass their definitions of done. Internally, Replay Lab remains the first milestone because portfolio-level decision impact depends on trustworthy session, decision, and valuation records.

The combined product flow is:

```text
Observe a hidden historical market state
  -> submit an immutable decision before advancing
  -> reveal candles one step at a time
  -> record every action and plan change
  -> separate process quality from financial outcome
  -> review behaviour patterns across sessions
  -> connect decisions to portfolio exposure and risk
  -> inspect return, risk, and attribution over time
```

## 2. Product Outcomes

The completed program must allow a user to:

1. Start a replay session with a chosen or randomized symbol, date, timeframe, capital base, maximum risk, and optional setup category.
2. See only market data and analytics available at the simulated timestamp.
3. Submit a Decision Ticket before revealing the next outcome-bearing candle.
4. Save, resume, complete, and review replay sessions without rewriting history.
5. Inspect process quality independently from profit or loss.
6. Record optional pre-decision and post-session behaviour reflections.
7. See private, rule-based behaviour observations across a sufficient number of sessions.
8. Inspect portfolio equity, return, drawdown, attribution, concentration, correlation, volatility, beta, and risk contribution.
9. Preview the portfolio impact of a Decision Ticket before submission.
10. Understand every metric through its formula, inputs, observation window, data quality, and limitations.

- Point-in-time portfolio snapshots and normalized snapshot holdings.
- Portfolio equity curve from persisted valuations.
- Absolute return, time-weighted return, money-weighted return, benchmark return, excess return, rolling volatility, maximum drawdown, recovery duration, turnover, average holding period, and cash drag.
- Return contribution by holding and sector.
- Realized and unrealized P&L decomposition.
- Single-stock and sector concentration.
- Correlation matrix, covariance matrix, portfolio volatility, beta, and component risk contribution.
- Configurable portfolio risk policy and explainable warnings.
- Pre-decision portfolio impact inside the V0.9 Decision Workbench preview.

### 3.3 Shared scope

- DTO-first APIs.
- Service-first business logic.
- Decimal-based money and risk calculations.
- Versioned formulas and deterministic outputs.
- Tenant isolation on every user-owned query and mutation.
- Optimistic concurrency on replay and decision mutations.
- Idempotency for advance, action, and snapshot capture commands.
- Clear partial-data and stale-data states.

### 3.4 Out of scope

- Broker connectivity or real-money execution.
- Short selling, derivatives, margin, or leverage.
- Portfolio optimization or automated rebalancing.
- Trade recommendations or predictive models.
- Psychological diagnosis, personality scoring, or clinical language.
- Social leaderboards or public behaviour profiles.
- New financial indicators not yet learned through Zerodha Varsity.
- Tick-level replay.
- Kafka, Spark, Iceberg, or a new external event store in this release.
- Full tax-lot accounting or tax reporting.
- Automatic deposits and withdrawals beyond the existing initial portfolio capital model.
- Treating a process score as a probability of profit.

## 4. Current Architecture and Constraints

The current application is a modular monolith:

```text
React 19 and TypeScript
  -> route-backed workspaces
  -> typed REST client
  -> FastAPI routes
  -> application services
  -> deterministic analytics services
  -> MarketDataService and MarketDataProvider
  -> SQLAlchemy operational storage
  -> Redis-compatible cache
```

Existing seams that will be reused:

- `ReplayEngine` already slices candles through the current step and evaluates analytics only on that slice.
- Existing public replay endpoints are stateless and allow arbitrary steps and timeline access.
- `DecisionJournalEntry` is the canonical immutable Decision Ticket aggregate.
- `DecisionTicketAmendment` provides append-only decision changes.
- `DecisionSnapshotService` captures point-in-time evidence and hashes the snapshot.
- `PositionSizingService` calculates transparent cash-equity risk limits.
- `PortfolioService` owns current holdings, cash, transactions, and live valuation.
- `PortfolioTransaction` is an immutable trade ledger.
- The in-memory event bus is an integration seam, but not durable event storage.
- React Router is installed and Decisions already use dedicated pages.

Important current limitations:

- Public replay timeline responses expose the complete historical timeline and therefore cannot power blind sessions.
- Replay progress is browser state and cannot be resumed.
- Portfolio history is reconstructed from current holdings and live prices rather than persisted valuation snapshots.
- Current contribution analytics describes only the latest daily move.
- Decision risk preview does not calculate post-decision portfolio concentration or incremental risk.
- The provider supports interval parameters, but historical availability varies by interval and source.

## 5. Combined Architecture

### 5.1 Bounded contexts

Keep four explicit application boundaries:

```text
Replay Lab
  owns sessions, cursor, actions, reflections, simulated fills, results

Decision Workbench
  owns immutable plans, evidence snapshots, risk snapshots, amendments

Portfolio Intelligence
  owns portfolio valuations, history, metrics, attribution, risk policy

Market Intelligence
  owns candles, patterns, structure, volume, fuzzy evidence, provenance
```

The contexts integrate through identifiers and service interfaces. They must not directly mutate each other's tables.

### 5.2 Durable records versus integration events

Replay actions require a durable database event ledger. The existing in-memory event bus is not sufficient because its history disappears on restart.

Use two layers:

1. `ReplaySessionEvent` rows are the durable, append-only audit source.
2. Existing `DomainEvent` objects are published after successful commits for telemetry and future Kafka integration.

Portfolio snapshots and transactions are durable facts. Derived metrics are reproducible projections over those facts and versioned market inputs.

### 5.3 Shared calculation envelope

Every analytics response must include:

- `formula_id`
- `formula_version`
- `observation_start`
- `observation_end`
- `observation_count`
- `inputs`
- `result`
- `unit`
- `data_quality`
- `limitations`

This envelope should be represented by a shared backend schema and a shared frontend type. It allows compact cards to show the result and a short explanation while an expanded view shows the full calculation.

### 5.4 Shared provenance contract

Replay and portfolio calculations must expose:

- Market data provider name
- Requested and resolved interval
- Source timestamp or valuation timestamp
- Latest market timestamp used
- Timezone
- Analytics version
- Candle or valuation fingerprint
- Staleness state
- Missing-symbol list
- Partial-result flag

## 6. Compact Visibility Product Rule

Compact visibility is a release-level constraint, not a styling task applied at the end.

### 6.1 Default surfaces

Each default page shows only:

- One primary status line
- Four to six key metrics
- At most three highest-priority warnings or observations
- One compact table or chart
- One clear action to open full analysis

No default card should contain a paragraph. Explanations on compact cards should normally remain within five to eight words.

### 6.2 Progressive disclosure

Use three levels:

1. Compact card: label, value, status, short explanation.
2. Expanded panel or full-screen overlay: formula, inputs, evidence, thresholds, data quality.
3. Dedicated review route: full event history, comparisons, charts, and audit details.

### 6.3 Replay Lab layout

Desktop layout:

```text
Header: session state, symbol visibility, simulated time, save state
Chart: dominant central surface
Compact right rail:
  Decision gate
  Risk state
  Three evidence cards
  Advance control
Bottom drawer on demand:
  Event history
  Full evidence
  Behaviour prompts
```

Do not place the complete evidence snapshot, score rubric, event history, and behaviour questionnaire beside the chart simultaneously.

### 6.4 Portfolio layout

Default overview:

```text
Header: total value, absolute return, drawdown, cash, data freshness
Primary area: equity curve and benchmark
Compact rail: top contributor, top detractor, top risk, top warning
Holdings table: symbol, value, return contribution, allocation, risk contribution
```

Detailed performance, attribution, risk, history, and formula views belong to tabs or child routes.

### 6.5 Responsive behaviour

- At 1024 pixels and above, use chart plus compact rail.
- From 768 to 1023 pixels, collapse the rail into a tabbed lower panel.
- Below 768 pixels, use stacked summary cards and a sticky action bar.
- Full analysis overlays must be scrollable, keyboard accessible, and closable with Escape.
- Tables must collapse nonessential columns rather than force horizontal overflow where possible.

## 8. Replay Session Lifecycle

### 8.1 Session creation

The create command accepts:

- Optional symbol or `randomize_symbol = true`
- Optional start date or `randomize_start = true`
- Timeframe
- Session length in bars
- Starting capital
- Maximum risk percentage
- Optional setup category
- Optional blind display flags

Server validation must:

1. Resolve the symbol against the supported universe.
2. Map timeframe to an allowed provider period and interval.
3. Load enough warmup candles for every active analytical engine.
4. Select a start index with sufficient warmup and future session bars.
5. Calculate a canonical dataset fingerprint.
6. Persist the session and initial event atomically.
7. Return only the initial visible state.

### 8.2 Timeframe policy

Use an explicit configuration map rather than accepting arbitrary provider strings.

Initial supported values should be:

- `1d`
- `1h` only when the provider can supply the requested historical window reliably
- `15m` only for provider-supported recent windows

If intraday data cannot satisfy warmup and session length, return `422 REPLAY_DATA_WINDOW_UNAVAILABLE` with supported alternatives. Do not silently switch timeframe.

### 8.3 Decision gate

A newly started session enters `AWAITING_DECISION`.

The advance command is rejected until:

- A valid Decision Ticket exists for the current decision cycle.
- Contradicting evidence has been acknowledged where present.
- Required pre-decision prompts are answered when enabled by the user.
- Entry plans pass risk validation.

The API returns `409 REPLAY_DECISION_REQUIRED`, not a generic validation error.

### 8.4 Advance command

The client sends only:

- Session ID
- Expected session version
- Idempotency key
- Advance count, default and maximum of one during an active position

The server owns `current_index`. The client cannot request an arbitrary future index.

The command:

1. Locks or version-checks the session.
2. Loads the exact dataset identified by the session fingerprint.
3. Reveals the next candle.
4. Appends `CANDLE_REVEALED`.
5. Evaluates entry activation, invalidation, target, and period end.
6. Appends resulting events and executions.
7. Recomputes only analytics visible at the new index.
8. Updates session cursor and version.
9. Commits atomically.
10. Publishes integration events after commit.

### 8.5 Same-bar ambiguity

Daily and intraday OHLC bars do not reveal the order of high and low within the bar.

Deterministic policy:

- If an entry trigger and invalidation are both touched in one bar, activate the entry first only when the open or prior close makes that ordering unambiguous. Otherwise mark the fill as ambiguous and apply the conservative adverse-first outcome.
- If target and invalidation are both touched after entry in one bar, apply invalidation first.
- The review page must display the ambiguity policy.
- A future lower-timeframe provider may replace this policy only through a new calculation version.

### 8.6 Pause and resume

Pause records an event and prevents advancement. Resume reconstructs visible state from:

- Session configuration
- Current cursor
- Dataset fingerprint
- Event sequence
- Linked decision
- Simulated executions

The resume response must never include future timeline items.

### 8.7 Completion

Completion reasons:

- `INVALIDATION`
- `TARGET`
- `USER_EXIT`
- `PERIOD_END`
- `NO_ENTRY`
- `ABANDONED`

Completion freezes outcome calculations, requests post-session reflection, and creates the result projection. Reflections added afterward are new events and may create a new result projection version without changing market outcome facts.

## 9. No-Look-Ahead Design

### 9.1 Separate legacy replay from Replay Lab

Keep the current public, stateless replay API for chart exploration. Do not use it inside Replay Lab.

Replay Lab must use authenticated session APIs that never return:

- Future timestamps
- Future closes or volumes
- Total timeline entries with price data
- Future events
- Future analytics
- Hidden randomized answer metadata before completion

It may return a count of remaining bars without returning their timestamps or values.

### 9.2 Server-owned market slice

Create `ReplaySessionStateService` that accepts a tenant-owned session and returns analytics for:

```text
all_candles[warmup_start_index : current_index + 1]
```

Only display candles at or after `start_index`. Warmup candles can feed indicators without appearing as newly revealed outcome candles. Provenance must state the warmup range.

### 9.3 Fingerprint verification

Compute the dataset fingerprint from canonicalized values:

- Symbol
- Interval
- Candle timestamps
- Open, high, low, close, volume
- Provider and adjustment mode

If a provider later returns different historical data for the same request, pause the session and return `409 REPLAY_DATASET_CHANGED`. Do not continue against silently revised data.

### 9.4 Explicit leakage tests

Tests must prove:

- Mutating any candle after the current index does not change the current state response.
- Current serialized responses contain no future timestamp or price.
- Randomized session metadata does not expose hidden future values.
- Scoring before completion does not access outcome fields.
- Resume produces the same state and hash as the original session.

## 10. Decision and Position Rules in Replay

### 10.1 Cash-equity boundary

V0.10 supports long cash-equity entries only. Bearish or neutral decisions may be recorded as `WATCH`, `AVOID`, `REDUCE`, or `EXIT`, but they do not open short positions.

### 10.2 Entry activation

For `ENTER` or `ADD`:

- The planned entry zone is immutable in the original ticket.
- A position activates when a newly revealed candle intersects the entry zone and the trigger conditions are marked satisfied.
- Default fill price is the least favorable valid price inside the zone under the configured conservative fill policy.
- Quantity comes from the server-verified risk snapshot unless the user explicitly selects a smaller quantity before activation.
- Increasing quantity beyond the verified maximum is rejected.

### 10.3 Amendments

Decision changes use the existing amendment model and also append a replay event containing:

- Original value
- New value
- User reason
- Replay index
- Simulated timestamp
- Newly available evidence hash

Moving invalidation farther from the entry is classified as risk widening. Tightening invalidation is recorded separately and must not be mislabeled as the same violation.

### 10.4 User exit

A user exit requires:

- Quantity or full-exit selection
- Reason category
- Optional explanation
- Evidence keys that motivated the exit, if any
- Expected session version

The exit event is append-only. The score evaluates whether the exit followed the plan, not whether a later candle would have produced more profit.

## 11. Process Scoring

### 11.1 Separation from outcome

The process score is a 0 to 100 rules-based rubric. Profit, loss, MFE, MAE, and realized R are excluded from the process-score formula.

Outcome metrics appear in a separate section and must never change the process score.

### 11.2 Initial scoring rubric

Version the rubric as `process-v1`:

| Component | Weight | Measurement |
|---|---:|---|
| Plan completeness and evidence discipline | 20 | Required plan fields, checklist completion, conflict acknowledgement |
| Risk planning and size compliance | 20 | Planned risk, actual risk, verified maximum quantity |
| Invalidation discipline | 20 | Original invalidation respected, no unacknowledged risk widening |
| Amendment discipline | 15 | Changes recorded before action with reason and new evidence |
| Entry adherence | 10 | Entry occurs only after the documented trigger and inside the zone |
| Exit adherence | 10 | Exit follows target, invalidation, or documented evidence-based rule |
| Reflection completion | 5 | Enabled pre-decision and post-session prompts completed |

Each component returns:

- Earned points
- Maximum points
- Status
- Rule IDs that fired
- Evidence event IDs
- Short explanation
- Full explanation

### 11.3 Outcome metrics

Report separately:

- Planned risk amount
- Actual initial risk amount
- Reward-to-risk at entry
- Maximum favourable excursion in price, currency, percent, and R
- Maximum adverse excursion in price, currency, percent, and R
- Realized P&L
- Realized R-multiple
- Entry slippage from planned zone midpoint
- Exit reason
- Bars held
- Target reached flag
- Invalidation reached flag
- Target changed after entry flag
- Invalidation widened after entry flag

For a long position:

```text
initial_risk_per_share = entry_price - original_invalidation_price
realized_r = (exit_price - entry_price) / initial_risk_per_share
mfe_r = (maximum_high_after_entry - entry_price) / initial_risk_per_share
mae_r = (minimum_low_after_entry - entry_price) / initial_risk_per_share
```

Weighted values must be used when multiple fills occur.

### 11.4 Score invariants

- A profitable session can have a low process score.
- A losing session can have a high process score.
- Recalculating unchanged events with the same scoring version produces identical output.
- Missing data lowers confidence or marks a component unavailable; it does not invent a neutral score.
- Score explanations identify exact events and thresholds.

## 12. Behaviour Review

### 12.1 Prompt model

Keep prompt definitions in versioned code configuration with stable keys.

Pre-decision prompt keys:

- `ANCHORING_CHECK`
- `CONTRADICTORY_EVIDENCE_CHECK`
- `RECENCY_CHECK`
- `POSITION_INDEPENDENCE_CHECK`
- `INVALIDATION_EVIDENCE`

Post-session prompt keys:

- `INVALIDATION_MOVED`
- `EXIT_REASON_REVIEW`
- `POST_LOSS_RISK_CHANGE`
- `OUTCOME_BIAS_CHECK`
- `FAILED_ASSUMPTION`

Responses are optional by default except prompts explicitly enabled as gates in session preferences.

### 12.2 Observation engine

Create a pure `BehaviourObservationService` that consumes replay events and returns private observations. It must use neutral, descriptive language.

Initial observations:

- Frequent invalidation widening
- Oversizing after a losing session
- Premature exits without a recorded evidence change
- High confidence with weak process adherence
- Repeated failure to acknowledge volume conflict
- Decisions taken in setup-regime mismatches

Every observation exposes:

- Observation key
- Plain-language statement
- Numerator and denominator
- Minimum sample threshold
- Applicable session IDs
- Rule and threshold
- Observation window
- Data-quality limitations

Do not show an observation before at least five eligible sessions. Use "not enough sessions" rather than drawing a conclusion.

### 12.3 Privacy

- Behaviour endpoints require authentication.
- Observations are scoped to the current user.
- No behaviour data appears in public market routes, system telemetry payloads, or logs.
- Free-text reflections must not be included in metrics labels or tracing attributes.
- Export and deletion should follow the same user-data lifecycle as decisions.

## 13. Replay Analytics

Aggregate completed, eligible sessions by:

- Setup category
- Market regime at decision time
- Confidence level
- Timeframe
- Symbol
- Checklist adherence band

Metrics:

- Session count
- Entry activation rate
- Win and loss distribution
- Average and median R
- Expectancy in R
- Standard deviation of R
- Cumulative R curve
- Maximum drawdown in cumulative R
- Process score distribution
- Most common process violations

Expectancy formula:

```text
expectancy_r = mean(realized_r across eligible completed sessions)
```

Always display sample size. Suppress grouped conclusions below the configured minimum sample count.

## 15. Portfolio Valuation and Performance

### 15.1 Valuation service

Create `PortfolioValuationService` to:

1. Load the tenant-owned portfolio and holdings.
2. Fetch quotes through `MarketDataService`.
3. resolve sector metadata from the NIFTY 50 catalogue.
4. Calculate holding and portfolio values with Decimal.
5. Fetch the aligned NIFTY 50 benchmark value.
6. Record freshness and missing data.
7. Build a canonical fingerprint.
8. Persist snapshot header and holdings atomically.

If some prices fail, persist a `PARTIAL` snapshot only when at least one holding is valued and clearly identify omitted holdings. Do not substitute zero prices.

### 15.2 Absolute return

For the current no-external-cash-flow portfolio model:

```text
absolute_return = (ending_value - starting_value) / starting_value
```

The response must state the starting snapshot and ending snapshot.

### 15.3 Time-weighted return

Implement geometrically linked subperiod returns:

```text
twr = product(1 + subperiod_return) - 1
```

Trades are internal cash-to-holding movements and are not external cash flows. The engine must still use a cash-flow-aware interface so deposits and withdrawals can be introduced later without redesign.

### 15.4 Money-weighted return

Use XIRR over dated external cash flows:

- Initial capital is an outflow at portfolio creation.
- Terminal portfolio value is an inflow at the observation end.
- Current V0.11 has no intermediate external flows unless a later cash-flow ledger is introduced.

Return unavailable with a precise explanation if the cash-flow signs do not permit a stable solution.

### 15.5 Benchmark and excess return

Use the NIFTY 50 index as the default benchmark through a dedicated benchmark symbol configuration.

```text
benchmark_return = end_benchmark_close / start_benchmark_close - 1
excess_return = portfolio_return - benchmark_return
```

Align benchmark observations to portfolio valuation dates using the latest market close at or before the snapshot timestamp. Show any alignment lag.

### 15.6 Volatility

Use simple daily returns from aligned valuation points and sample standard deviation:

```text
annualized_volatility = stdev(daily_returns) * sqrt(trading_periods_per_year)
```

The annualization factor must derive from timeframe configuration and appear in the formula details.

### 15.7 Drawdown

```text
drawdown_t = portfolio_value_t / running_peak_t - 1
maximum_drawdown = minimum(drawdown_t)
```

Recovery duration is the number of calendar days and observed valuation points from the trough until the prior peak is regained. If not recovered, return an open recovery state.

### 15.8 Turnover

```text
turnover = sum(abs(trade_value)) / average_portfolio_value
```

Expose whether one-way or two-way turnover is used. V0.11 uses the formula above and labels it explicitly.

### 15.9 Average holding period

Replay immutable transactions using deterministic FIFO lot matching solely for duration measurement. This does not change the existing weighted-average-cost P&L method.

Weight completed lot durations by quantity. Open lots are reported separately and excluded from completed holding-period averages.

### 15.10 Cash drag

Estimate benchmark-relative cash drag from prior-period cash weights:

```text
cash_drag = sum(-cash_weight_t_minus_1 * benchmark_return_t)
```

This means cash is a drag when the benchmark rises and a benefit when it falls. Label it as benchmark-relative, not an absolute loss.

## 16. Return Attribution

### 16.1 Daily contribution model

For each aligned interval:

```text
holding_contribution_i_t = beginning_weight_i_t * holding_return_i_t
cash_contribution_t = beginning_cash_weight_t * cash_return_t
```

Cash return defaults to zero. Sum contributions through time and retain an explicit residual for trades, missing observations, and rounding. The total must reconcile to portfolio return within a documented tolerance.

### 16.2 Attribution views

Provide:

- Contribution by symbol
- Contribution by sector
- Largest contributor
- Largest detractor
- Realized versus unrealized P&L decomposition
- Cash effect
- Allocation-change residual

Do not mix percentage-point return contribution and currency P&L in the same value. The UI should offer separate lenses.

## 17. Portfolio Risk Analytics

### 17.1 Return matrix

Build aligned daily return series for current holdings and the benchmark.

Rules:

- Use a common intersection of timestamps for covariance and correlation.
- Require the policy's minimum observation count.
- Report dropped dates and missing symbols.
- Do not forward-fill prices across long gaps.
- Return `INSUFFICIENT_DATA` instead of zero risk.

### 17.2 Covariance and correlation

Use sample covariance and Pearson correlation. Return matrix labels, observation count, range, and formula version.

### 17.3 Portfolio volatility

```text
portfolio_variance = weights_transpose * covariance_matrix * weights
portfolio_volatility = sqrt(portfolio_variance)
```

Annualize consistently with the return frequency.

### 17.4 Beta

```text
portfolio_beta = covariance(portfolio_returns, benchmark_returns)
                 / variance(benchmark_returns)
```

Return unavailable when benchmark variance is zero or observations are insufficient.

### 17.5 Component risk contribution

```text
marginal_contribution_i = (covariance_matrix * weights)_i / portfolio_volatility
component_contribution_i = weight_i * marginal_contribution_i
percent_risk_contribution_i = component_contribution_i / portfolio_volatility
```

Show the exact portfolio weights and observation range. Risk contribution may be negative for a diversifying holding and must not be clamped.

### 17.6 Concentration

Calculate:

- Maximum single-stock weight
- Sector weights
- Herfindahl-Hirschman concentration index as a descriptive metric
- Top three holdings weight

Warnings use configured policy thresholds and never imply a required trade.

## 23. Data Flow

### 23.1 Replay decision flow

```text
Create session
  -> resolve eligible dataset and fingerprint
  -> persist session and SESSION_CREATED
  -> return initial visible state
  -> start session
  -> require decision
  -> server previews evidence from session cursor
  -> user submits immutable ticket
  -> persist ticket plus DECISION_SUBMITTED atomically
  -> allow one-step advance
  -> append reveal and execution events
  -> complete session
  -> calculate process and outcome separately
  -> collect reflection
  -> show review
```

### 23.2 Portfolio snapshot flow

```text
Trade or valuation request
  -> load tenant portfolio
  -> fetch current prices and benchmark
  -> calculate Decimal valuation
  -> persist snapshot and holding rows atomically
  -> publish snapshot event
  -> invalidate portfolio analytics cache
```

### 23.3 Decision impact flow

```text
Decision preview with portfolio ID
  -> build market evidence
  -> calculate candidate quantity
  -> load latest portfolio snapshot and policy
  -> calculate projected exposures and risk
  -> return compact warnings plus full inspectable details
  -> submit only if market and portfolio context hashes still match
  -> store impact snapshot inside immutable ticket
```

## 25. Error Handling and Edge Cases

### 25.1 Replay

- Insufficient warmup bars: reject creation with supported alternatives.
- Delisted or missing symbol history: select another randomized candidate or return a clear failure for explicit symbols.
- Provider history revision: pause with dataset-changed conflict.
- Duplicate advance request: return the prior idempotent result.
- Two browser tabs advancing: one succeeds, one receives version conflict.
- No decision before advance: reject with decision-required conflict.
- No entry activation by end: complete as `NO_ENTRY` and omit trade outcome metrics.
- Zero or negative initial risk: reject the decision.
- Same-bar target and invalidation: conservative deterministic policy.
- Partial exit: maintain weighted remaining entry and immutable execution rows.
- Abandonment: retain all events and exclude from outcome aggregates unless explicitly requested.

### 25.2 Portfolio

- Empty portfolio: return valid zero-state overview and unavailable risk metrics.
- One holding: correlation matrix is 1x1; diversification observations are unavailable.
- Missing quote: mark snapshot partial and exclude the symbol from risk matrices with disclosure.
- Stale quote: value provisionally and surface age.
- Corporate actions or adjusted-history changes: fingerprint and version the source data.
- Benchmark gap: use prior close with explicit lag or mark unavailable when lag exceeds policy.
- Zero benchmark variance: beta unavailable.
- Too few observations: matrices and volatility unavailable, never zero.
- Negative cash: retain existing trade rejection and flag any legacy invalid state.
- Portfolio state changes during decision preview: require refresh.
- Floating-point legacy values: convert through string to Decimal.

## 26. Performance and Caching

- Cache session datasets by fingerprint, not only symbol and period.
- Cache current replay analytics by `(session_id, current_index, analytics_version)`.
- Do not cache user reflections or free text in shared caches.
- Fetch portfolio price history per unique symbol and observation range, then reuse it across performance, attribution, and risk services.
- Cache portfolio analytics by `(portfolio_id, latest_snapshot_id, policy_version, formula_version)`.
- Invalidate portfolio caches after trades, snapshot capture, or policy changes.
- Paginate replay events, sessions, and snapshots.
- Limit matrix endpoints to the portfolio's current holdings and a configured maximum symbol count.
- Avoid one database query per event or holding by eager loading and bulk queries.
- Compute large matrices outside request-critical database transactions.
- Keep compact overview endpoints lightweight and defer matrices and detailed formulas until their route or overlay is opened.

## 27. Security and Integrity

- Every Replay Lab and Portfolio Intelligence route requires authentication.
- Every query includes `user_id` or verifies ownership through a tenant-owned parent.
- Session IDs, decision IDs, event IDs, portfolio IDs, and snapshot IDs must be cross-checked for the same user.
- The server derives symbol, cursor, and market timestamp from the replay session.
- Client-supplied score, outcome, evidence snapshot, valuation, or matrix values are ignored.
- Use expected versions for replay session and policy mutations.
- Use database uniqueness for idempotency, not only application memory.
- Free-text behaviour responses must be excluded from logs and telemetry.
- Completed session events and portfolio snapshots are immutable through public APIs.

## 32. Final Architectural Position

This release must strengthen Xeroww's identity as an explainable reasoning and learning system.

Replay Lab is not a paper-trading game. Its purpose is to measure decision discipline under point-in-time information.

Portfolio Intelligence is not an optimization or recommendation engine. Its purpose is to explain how individual decisions combine into portfolio return, exposure, and risk.

Together they create the next major product loop:

```text
Evidence
  -> decision
  -> action history
  -> process review
  -> portfolio consequence
  -> explainable learning
```
