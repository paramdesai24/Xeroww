# Xeroww V0.9 Decision Workbench Implementation Plan

## 1. Purpose

This plan defines the implementation of Xeroww V0.9 as a cross-page Decision Workbench. The release will connect the existing market analysis, fuzzy explainability, candle forensics, journal, replay, and portfolio capabilities into a disciplined decision workflow.

V0.9 will not be implemented as one oversized journal page. It will introduce dedicated routes for the decision list, decision creation, and decision detail, with contextual entry points from the Market, Replay, and Portfolio workspaces.

The core lifecycle is:

```text
Observe market evidence
  -> open a contextual decision draft
  -> define thesis, horizon, entry, invalidation, target, and risk
  -> inspect supporting and contradicting evidence
  -> submit and freeze the original decision
  -> append later observations or lifecycle changes
  -> review the original decision without rewriting history
```

## 2. Product Outcomes

V0.9 must deliver the following user outcomes:

1. A user can start a decision from the current Market symbol, the current Replay candle, a Portfolio holding, or the Decisions workspace.
2. A user can define a structured cash-equity decision instead of entering only a free-text thesis.
3. Xeroww can calculate a transparent position-size and reward-to-risk preview for eligible entry plans.
4. Xeroww can show independent supporting, contradicting, contextual, and insufficient evidence.
5. The backend, not the browser, captures the authoritative market snapshot and provenance.
6. The submitted decision remains immutable. Later changes are stored as append-only amendments.
7. The user can inspect the complete original snapshot on a dedicated detail page.
8. Existing V0.8 journal entries remain readable and existing journal API consumers do not break.

## 3. Scope

### 3.1 In scope

- Dedicated frontend routes for Market, Decisions list, Decision creation, Decision detail, Portfolio, Watchlists, Alerts, and System.
- Conversion of the existing module-state navigation into URL-backed navigation.
- A structured Decision Ticket for cash-equity analysis.
- Server-generated point-in-time analytical snapshots.
- Deterministic evidence classification and transparent evidence counts.
- Position sizing and reward-to-risk calculations for eligible bullish entry plans.
- Optional portfolio capital and concentration context in the risk preview.
- Immutable submitted decision fields.
- Append-only amendments and audited status changes.
- Legacy journal compatibility and migration.
- Tenant isolation for all decision data.
- Responsive desktop, tablet, and mobile layouts.
- Backend and frontend regression coverage.
- Version updates from V0.8 to V0.9 after the feature is complete.

### 3.2 Out of scope

- Broker connectivity or real order placement.
- Automatic trade execution from a Decision Ticket.
- Futures, options, margin, leverage, or short-selling workflows.
- Persisted replay sessions and behavioural scoring. Those belong to V0.10.
- Portfolio equity curves, portfolio optimization, covariance, or attribution. Those belong to V0.11.
- New RSI, MACD, Bollinger, ADX, CPR, Fibonacci, or Dow Theory engines.
- A single unexplained technical or fundamental score.
- Kafka, Spark, Iceberg, WebSocket streaming, or external event infrastructure.
- Editable submitted plans.
- Tax advice or financial recommendations.

## 4. Current Architecture and Constraints

The current application is a modular monolith:

```text
React 19 client
  -> unversioned REST endpoints through /api at the edge
  -> FastAPI routes
  -> application services
  -> deterministic analytics and fuzzy orchestrators
  -> MarketDataService
  -> configured MarketDataProvider

User state
  -> SQLAlchemy models
  -> SQLite in local development and tests
  -> PostgreSQL in production-like deployment
  -> Alembic as schema authority
```

Relevant existing behavior:

- `dashboard/src/App.tsx` owns the active module, market data, replay state, and modal state.
- Module navigation changes React state rather than the browser URL.
- `DecisionJournalEntry` stores symbol, action, thesis, a JSON context snapshot, status, and timestamps.
- `/journal` supports list, create, detail, update, and thesis review.
- `JournalService` applies tenant scoping.
- `AnalyticsOrchestrator` creates market structure summaries.
- `FuzzyOrchestrator` creates deterministic Mamdani explainability reports.
- `ReplayEngine` evaluates a candle slice without future data.
- `PortfolioService` provides cash, holdings, and live portfolio valuation.
- The frontend has no routing dependency today.

The implementation must preserve these boundaries and avoid moving business calculations into React components or FastAPI routes.

## 5. Architecture Decisions

### 5.1 Evolve the journal aggregate

The existing `decision_journal_entries` table will remain the aggregate root and database table. It will be extended into the V0.9 Decision Ticket rather than replaced with an unrelated table.

Reasons:

- Existing user data is preserved.
- Existing tenant-isolation behavior remains applicable.
- Existing thesis review and journal event integration can be evolved incrementally.
- The product retains one decision history instead of splitting journal entries and tickets.

The Python model may be renamed to `DecisionTicket` only if a compatibility alias named `DecisionJournalEntry` is retained during V0.9. The physical table must not be renamed in this release.

### 5.2 Canonical decisions API with journal compatibility

New functionality will use `/decisions` as the canonical API namespace. Existing `/journal` endpoints remain compatibility endpoints.

Compatibility rules:

- Existing legacy entries have `ticket_version = 0`.
- New V0.9 entries have `ticket_version = 1`.
- Legacy entries remain readable from both the old journal view contract and the new decision detail adapter.
- Legacy thesis editing continues only for version 0 entries.
- `/journal/{id}` must reject thesis mutation for version 1 entries with HTTP 409.
- Status changes on version 1 entries must use the decision lifecycle service and record an amendment.
- The new frontend must call `/decisions`, not `/journal`.

### 5.3 Submitted decisions are immutable

No server-side draft row is required in V0.9. A draft exists in the browser until submission.

After submission, the following fields never change:

- Symbol
- Direction
- Intent
- Holding period
- Setup classification
- Entry trigger
- Entry zone
- Invalidation level
- Target range
- Maximum risk percentage
- Maximum allocation percentage
- Confidence
- Thesis
- What would change my mind
- Supporting evidence selections
- Contradicting evidence acknowledgements
- Market snapshot
- Provenance
- Snapshot hash

Later observations, revised ideas, and lifecycle changes are append-only amendments. The aggregate's current lifecycle status may change, but every transition must create an amendment in the same database transaction.

### 5.4 Server-authoritative snapshots

The frontend may request and display a preview, but it must never submit a client-constructed analytical snapshot as truth.

On final submission, the backend must:

1. Normalize the symbol.
2. Fetch candles through `MarketDataService`.
3. truncate candles at the requested point in time when the source is replay.
4. Run market structure analysis on the eligible slice.
5. Run fuzzy inference on the exact same slice.
6. Build normalized evidence items.
7. calculate risk from validated decision inputs.
8. Build provenance and data-quality metadata.
9. Serialize the snapshot canonically.
10. Compute a SHA-256 snapshot hash.
11. Persist the ticket, snapshot, and evidence selections atomically.

For live mode, the client sends the candle timestamp shown during preview. If the latest eligible candle changes before final submission, the API returns HTTP 409 with code `MARKET_CONTEXT_CHANGED`. The frontend then reloads the preview and asks the user to review the changed evidence before resubmitting.

### 5.5 No opaque master score

Evidence will remain individually inspectable. V0.9 may present a rule-count summary, but it must not calculate a mysterious composite score.

Allowed evidence summaries:

- `STRONG_ALIGNMENT`
- `PARTIAL_ALIGNMENT`
- `MIXED`
- `WEAK_SUPPORT`
- `INSUFFICIENT_DATA`

The response must expose the aligned, conflicting, contextual, and insufficient counts used to select the label.

### 5.6 Cash-equity intent model

Direction and intent are separate:

- Direction: `BULLISH`, `BEARISH`, or `NEUTRAL`
- Intent: `ENTER`, `ADD`, `HOLD`, `REDUCE`, `EXIT`, `WATCH`, or `AVOID`

V0.9 validation rules:

- `ENTER` and `ADD` require `BULLISH` direction.
- `BEARISH` decisions may use `REDUCE`, `EXIT`, `WATCH`, or `AVOID`.
- `NEUTRAL` decisions may use `HOLD`, `WATCH`, or `AVOID`.
- V0.9 does not interpret a bearish decision as a short sale.
- Position sizing is available only for `ENTER` and `ADD`.

This makes the product useful for cash equities without accidentally introducing derivatives or short-selling semantics.

### 6.4 Contextual entry points

#### Market workspace

Add a `Plan Decision` action near the chart workspace actions. It navigates to:

```text

```

Add a `Review Decision` action on each holding row and a contextual action above the simulated trade form. It navigates with `symbol`, `source=portfolio`, and `portfolioId`.

#### Decisions workspace

### 6.5 Decisions list page

The list page replaces the current all-in-one `JournalView` form and cards.

It contains:

- Summary counts for open, closed, and cancelled decisions.
- Filters for symbol, status, direction, intent, source context, and date range.
- Sort by newest, oldest, confidence, and symbol.
- A responsive table on desktop.
- Compact decision cards on mobile.
- Legacy badge for migrated V0.8 entries.
- Evidence summary label and visible aligned/conflict counts.
- Snapshot data-quality state.
- Direct links to the detail page and Market symbol.

List responses must omit the full snapshot and amendment payloads to keep the endpoint small.

### 6.6 Decision creation page

Use one routed page with clearly separated sections rather than a modal. On wide screens, use a two-column layout with the form on the left and live evidence/risk preview on the right. On smaller screens, stack the sections.

Sections:

1. Context
   - Symbol
   - Source context
   - Snapshot as-of candle
   - Data-quality state
2. Decision
   - Direction
   - Intent
   - Intended holding period
   - Setup classification
   - Confidence from 1 to 5, explicitly labelled as user confidence
3. Plan
   - Entry trigger
   - Entry zone low and high
   - Invalidation price
   - Target range low and high
   - What would change my mind
4. Risk
   - Portfolio selection or manual capital base
   - Maximum capital risk percentage
   - Maximum allocation percentage
   - Deterministic position-size preview
5. Evidence
   - Supporting items
   - Contradicting items
   - Context-only items
   - Insufficient-data items
   - Explicit conflict acknowledgement
6. Thesis
   - Written rationale
   - Final confirmation of immutability

The form uses a reducer or dedicated `useDecisionDraft` hook. Do not spread dozens of unrelated `useState` calls across the page.

Persist an unsent draft in `sessionStorage`, keyed by source, symbol, replay timestamp, and user ID. Clear it after successful submission. Do not use persistent local storage for sensitive thesis content.

Warn before leaving a dirty form. If the router version supports a stable blocker API, use it. Otherwise, use `beforeunload` plus an in-app confirmation component for internal navigation.

### 6.7 Decision detail page

The detail page is the permanent audit view and contains:

- Identity header: symbol, direction, intent, status, confidence, holding period, creation time.
- Original plan: entry, invalidation, target, trigger, thesis, and change-mind condition.
- Risk-at-creation panel.
- Evidence summary with all evidence items expanded on demand.
- Full snapshot sections for structure, volume, moving averages, patterns, regime, signal alignment, and fuzzy dimensions.
- Data provenance: provider, candle range, bar count, calculation timestamp, algorithms, snapshot schema version, and hash.
- Amendment timeline.
- Lifecycle actions: close or cancel with a required reason.
- `Open Market` action for the symbol.
- Existing objective thesis review, clearly separated from the immutable original snapshot.

Legacy entries show available legacy fields and an explicit note that their V0.8 snapshot may be incomplete.

## 8. Backend Services

### 8.1 `DecisionSnapshotService`

Create `api/services/decision_snapshot_service.py`.

Responsibilities:

- Normalize the symbol through the configured provider boundary.
- Fetch the required candle range through `MarketDataService`.
- Select the point-in-time candle slice.
- Run all analytics on the same slice.
- Run fuzzy inference on the same slice.
- Capture the latest eligible candle and optional current quote context.
- Build provenance and data-quality metadata.
- Call `DecisionEvidenceService`.
- Produce stable canonical JSON and its hash.

Snapshot shape:

```text
metadata
  schema_version
  captured_at
  requested_source
  requested_as_of
  resolved_as_of
  timeframe
  period
  provider
  transport
  source_candle_range
  bar_count
  algorithm_versions
  data_quality
market
  current_candle
  quote_context
structure
  support_resistance
  volume
  moving_averages
  market_regime
  signal_alignment
  detected_patterns
  contextual_pattern
fuzzy
  dimensions
  overall_label
  overall_activation
  methodology_note
evidence
  summary
  counts
  items
```

Rules:

- `resolved_as_of` is always the actual candle used, not merely the requested timestamp.
- Replay uses candles whose timestamp is less than or equal to `asOf`.
- A replay request before the first candle returns 422.
- A requested future date resolves only to the latest available candle and is labelled accordingly.
- No quote fetched after `resolved_as_of` may influence replay evidence.
- The hash is calculated from sorted-key JSON using fixed decimal serialization and excluding request IDs or other nondeterministic transport fields.
- `captured_at` is stored in the snapshot but excluded from the deterministic analytical-content hash, or placed in a separately hashed envelope. Select one policy and test it explicitly. Preferred policy: hash the analytical payload and provenance inputs, excluding server capture time.

### 8.2 `DecisionEvidenceService`

Create `api/services/decision_evidence_service.py` as a pure deterministic service.

Input:

- Decision direction and intent
- Market structure summary
- Fuzzy report
- Current candle
- Data-quality metadata

Each evidence item contains:

- Stable key
- Category
- Source engine
- Observation label
- Raw value or structured values
- Human-readable explanation
- Directional stance: bullish, bearish, neutral, or unavailable
- Relationship to the user's direction: aligned, conflicting, contextual, or insufficient
- Methodology note
- Relevant algorithm version

Minimum evidence categories:

- Pattern and required context
- Market regime
- Swing structure
- Support proximity
- Resistance proximity
- Volume and RVOL
- Moving-average position
- Moving-average relationship
- Signal alignment
- Fuzzy momentum
- Fuzzy volume
- Fuzzy trend
- Fuzzy structure
- Data sufficiency and freshness

Summary rules must be constants with tests and documentation. Suggested initial rules:

- `INSUFFICIENT_DATA`: any required analytical domain is unavailable or snapshot quality is unavailable.
- `STRONG_ALIGNMENT`: at least 4 directional items align, no more than 1 conflicts, and no critical insufficiency exists.
- `PARTIAL_ALIGNMENT`: at least 2 items align and aligned items outnumber conflicts.
- `MIXED`: at least 2 items align and at least 2 conflict, or counts are equal with directional evidence present.
- `WEAK_SUPPORT`: fewer than 2 items align, or conflicts outnumber aligned items.

These are evidence counts, not outcome probabilities. The API and UI must say so.

### 8.3 `PositionSizingService`

Create `api/services/position_sizing_service.py` as a pure service using `Decimal` internally.

For `ENTER` and `ADD`:

- Planned entry price is the high end of the entry zone for a conservative bullish calculation.
- Risk per share is `planned_entry_price - invalidation_price`.
- Conservative target price is the low end of the target range.
- Reward per share is `target_price - planned_entry_price`.
- Maximum risk amount is `capital_base * max_risk_pct / 100`.
- Risk-limited quantity is the floor of `maximum_risk_amount / risk_per_share`.
- Cash-limited quantity is the floor of `available_cash / planned_entry_price` when a portfolio is selected.
- Allocation-limited quantity is the floor of `(capital_base * max_allocation_pct / 100) / planned_entry_price` when configured.
- Recommended quantity is the minimum positive applicable limit.
- Capital deployed is `quantity * planned_entry_price`.
- Potential loss is `quantity * risk_per_share`.
- Potential reward is `quantity * reward_per_share`.
- Reward-to-risk is `reward_per_share / risk_per_share`.
- The response states which constraint limited the quantity.

Validation:

- Entry zone low must be less than or equal to entry zone high.
- Invalidation must be below entry zone low for bullish entry plans.
- Target zone low must be above entry zone high.
- Target zone high, when provided, must be at least target zone low.
- Risk percentage must be greater than 0 and no greater than a configured safe maximum. Use 5 percent as the default server maximum unless an existing setting provides a stricter value.
- Allocation percentage must be greater than 0 and no greater than 100.
- Capital base, prices, and resulting quantities must be positive.
- A calculated quantity of zero is a valid warning response, not a server error.

For non-entry intents, return `not_applicable` with a reason instead of fabricating a position size.

The response must include formula version `POSITION-SIZING-V1`, inputs, outputs, rounding policy, and warnings.

### 8.4 `DecisionService`

Create `api/services/decision_service.py` and gradually delegate legacy `JournalService` operations to it where contracts overlap.

Responsibilities:

- Tenant-scoped list and detail queries.
- Preview orchestration.
- V0.9 validation.
- Snapshot rebuilding on submission.
- Preview candle consistency check.
- Evidence-key verification.
- Position-risk calculation.
- Atomic ticket creation.
- Append-only amendment creation.
- Validated status transitions.
- Optimistic concurrency using the `version` field.
- Legacy response adaptation.

Allowed status transitions:

- OPEN to CLOSED
- OPEN to CANCELLED
- CLOSED and CANCELLED are terminal in V0.9

Every transition requires a reason, inserts a status amendment, increments `version`, and sets `closed_at` where applicable.

### 8.5 Events

Extend `api/events/journal_events.py` or introduce `api/events/decision_events.py` with:

- `DecisionTicketSubmitted`
- `DecisionTicketAmended`
- `DecisionTicketClosed`
- `DecisionTicketCancelled`

Event payloads contain identifiers and safe summary fields, not the entire snapshot or thesis text. Publish only after a successful database commit. Event publication failure must be logged, not silently ignored, and must not roll back an already committed user transaction.

## 9. API Contracts

Create `api/schemas/decision.py` and `api/routes/decisions.py`.

### 9.1 Preview

`POST /decisions/preview`

Request includes:

- Symbol
- Direction
- Intent
- Holding period
- Entry and risk fields currently entered
- Optional portfolio ID
- Source context
- Optional replay as-of and period

Response includes:

- Resolved symbol and as-of candle
- Snapshot data quality
- Normalized evidence items and count summary
- Position sizing preview
- Snapshot preview hash
- Preview warnings

The preview is not persisted.

### 9.2 Create

`POST /decisions`

Request includes all immutable plan fields, selected evidence keys, acknowledged conflict keys, the expected as-of candle, and source context.

The server rebuilds the snapshot. It rejects unknown evidence keys and requires every automatically classified conflict to be either acknowledged or accompanied by an explicit user note. The exact requirement should be:

- All conflicts are visible.
- Submission requires one global `conflicts_reviewed = true` confirmation.
- The user may additionally select the conflicts most important to the thesis.

Response is the full decision detail and returns HTTP 201.

### 9.3 List

`GET /decisions`

Query parameters:

- `status`
- `symbol`
- `direction`
- `intent`
- `source_context`
- `created_from`
- `created_to`
- `sort`
- `skip`
- `limit`, capped at 100

Return a paginated object containing `items`, `total`, `skip`, and `limit`. Each item is a summary DTO and excludes `context_snapshot` and `risk_snapshot` internals.

### 9.4 Detail

`GET /decisions/{decision_id}`

Returns:

- Full original ticket
- Full snapshot
- Risk snapshot
- Evidence selections
- Amendment timeline
- Current lifecycle status and version
- Legacy marker

### 9.5 Amendment

`POST /decisions/{decision_id}/amendments`

Request:

- Amendment type
- Reason
- Structured payload
- Expected aggregate version

The endpoint never updates the original plan.

### 9.6 Status transition

`POST /decisions/{decision_id}/status`

Request:

- Target status
- Required reason
- Expected aggregate version

Return HTTP 409 for stale versions or invalid terminal transitions.

### 9.7 Review

`GET /decisions/{decision_id}/review`

Adapt the existing `ThesisReviewService`. It must use the original `source_as_of` rather than the row creation date when available. The review remains an objective later observation and must not rewrite the original snapshot.

## 11. Data Flow and Control Flow

### 11.1 Market to decision creation

```text
User clicks Plan Decision
  -> router opens /decisions/new with symbol and source
  -> DecisionCreatePage parses and validates query parameters
  -> preview API requests server snapshot
  -> DecisionSnapshotService obtains cached candles
  -> analytics and fuzzy engines run on one candle slice
  -> evidence service classifies independent observations
  -> risk service calculates only when enough valid inputs exist
  -> page displays evidence, conflicts, provenance, and warnings
  -> user submits
  -> server rebuilds and validates the snapshot
  -> server checks expected candle and evidence keys
  -> transaction persists immutable ticket
  -> domain event publishes after commit
  -> frontend redirects to /decisions/{id}
```

### 11.2 Replay to decision creation

```text
Replay is at candle N
  -> navigation includes resolved candle timestamp and period
  -> server fetches historical candles
  -> server keeps only candles at or before the timestamp
  -> all indicators and fuzzy evidence use the truncated slice
  -> snapshot provenance records the resolved range and bar count
```

No full-series indicator value may enter the replay decision snapshot.

### 11.3 Amendment flow

```text
User opens detail page
  -> submits observation or lifecycle change with expected version
  -> service verifies tenant and current version
  -> service inserts immutable amendment
  -> status changes only when requested and valid
  -> aggregate version increments
  -> transaction commits
  -> event publishes
  -> detail page reloads timeline
```

## 12. Validation and Error Handling

### 12.1 Request validation

- Normalize symbols to uppercase through the provider.
- Limit thesis and reason lengths to prevent unbounded payloads.
- Reject NaN, infinity, negative prices, and invalid decimal precision.
- Validate direction and intent combinations.
- Require structured plan fields for enter/add.
- Allow watch, avoid, hold, reduce, and exit tickets to omit position-sizing fields where not meaningful.
- Require `change_mind_condition` for all V0.9 tickets.
- Require conflict review before submission.
- Verify that the selected portfolio belongs to the current user.
- Verify that evidence keys exist in the server-generated snapshot.
- Never accept a client-provided snapshot object as authoritative.

### 12.2 Error responses

Use stable error codes in the existing structured error envelope where possible:

- `DECISION_NOT_FOUND`
- `INVALID_DECISION_INTENT`
- `INVALID_PRICE_PLAN`
- `PORTFOLIO_NOT_FOUND`
- `MARKET_CONTEXT_CHANGED`
- `INSUFFICIENT_MARKET_DATA`
- `UNKNOWN_EVIDENCE_KEY`
- `CONFLICTS_NOT_REVIEWED`
- `IMMUTABLE_DECISION`
- `INVALID_STATUS_TRANSITION`
- `DECISION_VERSION_CONFLICT`
- `MARKET_DATA_UNAVAILABLE`

Frontend errors must preserve the draft and provide an actionable recovery path.

### 12.3 Provider and partial-analysis failures

- Complete market-data failure prevents submission and returns 503.
- A missing optional engine result appears as insufficient evidence if the core candle series is valid.
- If a critical required domain cannot be computed, the snapshot is `INSUFFICIENT_DATA`.
- A user may create WATCH or AVOID decisions with insufficient evidence after explicit acknowledgement.
- ENTER or ADD must be blocked when current price, entry plan, or risk calculation is unavailable.
- Data freshness must say delayed, stale, unavailable, or partial. It must never say live for Yahoo data.

## 13. Performance Considerations

- Reuse `MarketDataService` candle and quote caches.
- Build structure and fuzzy evidence from one candle slice in one snapshot service call.
- Avoid calling separate public HTTP endpoints from the backend to assemble a snapshot.
- Keep preview responses bounded by excluding moving-average series points when the UI does not require the full series.
- Store one immutable snapshot per submitted decision. Do not duplicate it in amendment rows.
- Use summary DTOs for list pages.
- Lazy-load decision pages and the large snapshot inspector.
- Cancel stale preview requests in the browser.
- Do not add Redis-specific decision state in V0.9.
- Measure preview latency. A reasonable local target is p95 under 500 ms on cached candle data, excluding first provider fetch.

## 14. Security and Privacy

- Every decision and amendment query must include `user_id` scoping.
- Portfolio lookup must include the same user ID.
- Decision IDs must not grant access across tenants.
- Do not put thesis text into domain-event logs.
- Escape user text through React's normal rendering and never render it as raw HTML.
- Do not include access tokens in session-storage drafts.
- Keep draft storage scoped to the authenticated user and clear it on logout.
- Limit list size and text payload lengths.
- Preserve current authentication and rate-limit middleware.

## 18. Definition of Done

V0.9 is complete only when:

- Decisions have dedicated list, create, and detail routes.
- The Market, Replay, Portfolio, and Decisions pages can start the same typed workflow.
- Submitted decision fields and analytical snapshots cannot be edited.
- Amendments and status changes are append-only and tenant-scoped.
- The server creates every authoritative snapshot and verifies evidence selections.
- Replay-origin snapshots pass explicit no-look-ahead tests.
- Position sizing exposes formulas, inputs, outputs, rounding, and limiting constraints.
- Evidence remains independently inspectable and no master probability score is introduced.
- Legacy journal entries remain accessible.
- Direct deep links work in development and the container deployment.
- Backend and frontend automated tests pass.
- Alembic migration checks pass.
- Responsive visual verification passes.
- Documentation accurately distinguishes V0.9 from future V0.10 and V0.11 capabilities.

## 19. Deferred Follow-up for V0.10

The V0.9 model deliberately creates the seams needed by Replay and Behaviour Lab:

- Stable decision IDs
- Immutable initial plans
- Point-in-time snapshot timestamps
- Snapshot hashes
- Append-only amendments
- Decision versions
- Explicit evidence selections and conflicts
- Deterministic risk snapshots

V0.10 can associate these tickets with persisted replay sessions and compute process metrics without redesigning or mutating the original V0.9 decisions.
